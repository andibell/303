# BOM Pilot

A self-contained demonstration of a materials request workflow, built for a Protogen P303 mobile-experience case study. It uses synthetic sample data only and has no connection to external systems. See [BRIEF.md](./BRIEF.md) for the full product brief, including deliberate scope boundaries.

## Project overview

BOM Pilot helps a **Product Commercialization Manager** define the existing materials a new product needs and assemble a complete material request, without navigating the complexity of the underlying enterprise process. The manager answers business-oriented questions; the application translates those answers into the structured Request Items an execution team ultimately needs.

## Primary user

Product Commercialization Manager — represented in the build as the **Requestor** demo role. (A second demo role, **Execution Specialist**, represents the downstream team that works submitted requests; it exists to show role-based access, not as this brief's primary user.)

## Focused scenario

**New Product using existing materials.** In the application's own terms: Business Need **"New Product / Innovation"** with Material Scenario **"No New Materials."** This is the only business-need / material-scenario combination that is functional end to end in this build. Every other combination is selectable in Intake but is labeled "Planned for a future phase" and cannot proceed to Request Setup.

## Product principle

**Business Need establishes the starting experience.** Intake's first question is "What is the business need for this request?" — the answer determines which follow-up questions, uploads, and Request Items the product shows next, before anything about materials or structure is asked.

Enterprise complexity is intentionally handled behind the experience rather than exposed to the user: the Requestor enters a Source Material Identifier, not the final Execution Identifier the execution team later records; Request Items are led by a plain business name ("Create Finished Product") with the system-facing technical label shown secondary; and fields sourced from reference data or generated by the application are marked with a provenance indicator instead of asking the user to know where a value came from.

## Current implemented experience

What works today, end to end through the UI:

- **New Request** creates one Draft and opens Intake.
- **Intake** — request name; Business Need (six options, only New Product / Innovation is functional); Material Scenario (four options, shown only for New Product / Innovation, only No New Materials is functional); business justification; an optional, simulated reference-document upload (file metadata only, no file content is stored); progressive field validation; Save Draft.
- **Request Setup** — for the functional path, three Request Items are generated (Create Finished Product, Set Up Plant Availability, Build Product BOM). The Requestor can add a removed item back, remove an item (with a preview of what the removal affects), edit each item's fields with live validation and a generated Material Description, and rename the request in place. The item list collapses to a summary on narrow screens; a sticky action bar keeps Save Draft reachable.
- **BOM Work** — Drafts, Requests, and Completed lists (scoped to what each role may see), with search, a sortable table on wider screens and a compact list on narrow ones. Requests and Completed show pre-seeded demonstration records so a reviewer can see what a submitted, in-progress, action-required, or completed request looks like.
- **Role switching** between Requestor and Execution Specialist, with route access enforced and explained when a view isn't available to the current role.
- **Reports** appears in navigation but is marked "Planned" and has no functionality behind it.

**Not implemented as working screens:** Review & Submit, a request's record view, a Request Item's execution-data view, and the execution package view are all reachable from the UI but render a clearly labeled "outside the current review scope" placeholder rather than working functionality. **There is currently no control in the application that submits a request** — a request only appears as submitted, in progress, returned, or completed in BOM Work if it was pre-seeded that way as demo data.

The underlying domain and store logic (`src/domain`, `src/store`) does implement submission, execution start, return/"Action Required", resubmission, and completion, and this logic is exercised by the automated test suite and used to build the seeded demo records — but it is not yet wired to a working screen a reviewer can click through.

## Intended core flow

The brief's target flow (see [BRIEF.md](./BRIEF.md) for full detail) is:

**Start Request → New Product → Product Details → Existing Materials → Product Structure → Validation → Review → Submit → Confirmation**

Mapped to this build: *Start Request* through *Product Structure* are implemented as New Request, Intake, and Request Setup, with validation running continuously as part of Request Setup. *Review*, *Submit*, and *Confirmation* are represented only by a stage in the authoring stepper and a scope placeholder — they are intended product flow, not current functionality.

## Mobile-first intent

The authoring experience (Intake and Request Setup) is designed primarily for roughly 375–430px mobile widths, for a user working between meetings, referencing product information elsewhere, completing the task in short bursts, one-handed, and expecting to be interrupted. This shapes the implementation: one choice group shown at a time, full-width touch targets for choices, a persistent stage stepper and status chips for progress, mostly short or constrained text fields rather than open free text, single-column item authoring instead of a data grid, no actions that depend on hover, and no horizontal scrolling at phone widths.

## Conditional behavior

Implemented in the current build:

- Choosing a Business Need other than "New Product / Innovation" hides the Material Scenario question and shows a "planned for a future phase" notice instead of request context.
- Business justification, the reference-document upload, and the generated item template preview appear only once the path is functional.
- Once any Request Item exists, or Intake has been handed off, Business Need and Material Scenario are locked.
- In Create Finished Product, answering "Yes" to "Product Bill of Materials Setup Needed?" reveals the "Reference document link" field.
- Build Product BOM's header and component fields are only relevant when BOM setup is needed.
- A cross-item rule requires either a Build Product BOM item or a reference-document link when BOM setup is needed.

## Synthetic / public-safe data

This public repository contains generalized validation rules and fictional sample reference data only (facility codes like `FAC-01`, material numbers like `MAT-001`, generic unit and material-type lists), explicitly labeled in the code as synthetic demo data with no connection to a live system. Demo personas ("Demo Requestor", "Demo Executor") are generic role placeholders, not real people.

It intentionally excludes client-specific source material, interview transcripts, client branding, supplied or proprietary fonts, original project screenshots, real SAP or other system identifiers, proprietary taxonomy, and any confidential metrics.

## Validation

Exact commands from `package.json`:

```sh
npm run typecheck     # tsc -b
npm run lint          # eslint .
npm run test          # vitest run
npm run test:watch    # vitest (watch mode)
npm run build         # tsc -b && vite build
npm run check         # typecheck && lint && test && build
npm run verify:review # checks dist/ opens from file:// with no server/network
npm run build:review  # build && verify:review
```

As of this review, `npm run check` passes in full: **18 test files, 332 tests**, followed by a clean typecheck, lint, and production build. `npm run verify:review` also passes against the resulting `dist/`.

## Key test scenarios

Scenarios genuinely exercised by the current application and its test suite include:

- Intake's conditional reveal of Material Scenario, and locking of Business Need / Material Scenario once Request Items exist or Intake is complete.
- Progressive validation: untouched fields and items show no issues; issues appear once a field is touched; submission validation still reports every blocking issue regardless of what the UI has shown.
- Generating, deriving, and displaying the Material Description from structured attributes, and marking reference-sourced or generated fields with provenance indicators.
- The distinction between a Requestor-entered Source Material Identifier and an execution-recorded Execution Identifier.
- Adding and removing Request Items, including a removal preview, dependency messaging, and focus management after add/remove/select.
- Role-based route access and view switching between Requestor and Execution Specialist.
- BOM Work's lifecycle grouping (Drafts / Requests / Completed), search, and role-scoped visibility of pre-seeded demo records.
- Append-only request history.

The submission, execution, return/"Action Required", and completion lifecycle is covered by domain- and store-level tests (and used to build the seeded demo records), but — as noted above — is not yet reachable by clicking through the UI.

## Accessibility

Implemented in the current build:

- Form fields and choice groups use semantic `fieldset`/`legend` and `FormLabel`/`FormHelperText`, wired via `aria-describedby`.
- Failed validation on Continue moves focus to the first invalid field; adding, removing, or selecting a Request Item moves focus to the relevant heading or control.
- The stage stepper and navigation expose `aria-current`; a completed stage is marked with an icon plus a visually hidden "(completed)" label, not color alone.
- `StatusChip` always pairs an icon with a text label, for every status tone.
- A "Skip to main content" link is available at the top of every page.
- Request Item cards are confirmed keyboard-operable in the test suite.
